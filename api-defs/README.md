# What TrueNAS says about its API, and what it leaves out

`truenas-methods-<version>.json` is a TrueNAS's own description of its API: every method it has, with what each takes and what each answers. It is the answer to `core.get_methods`, taken as an administrator on a NAS of that version with `midclt call core.get_methods`, and named for the release it was taken from.

| | |
|---|---|
| `truenas-methods-25.10.7.json` | TrueNAS 25.10.7: 769 methods in 114 groups |
| `truenas-secrets-25.10.7.json` | where the secrets are in those methods: 1,040 places in 135 of them |

Neither holds anything of the NAS it was taken from: no names, addresses or settings, only the API's shape.

## Where the secrets are

The description does not say which values are secrets. The TrueNAS source does, so `truenas-secrets-<version>.json` is made from the source at the release's tag by `make secrets` (`sdk/pandorest/secrets.go`), which reads it without running it, follows every method to what it takes and answers, and checks every place it finds against the description. It followed all 769 methods of 25.10.7 and found nothing the description lacks. It reads only as much Python as the secrets are written in, and fails on a file of the source it cannot read rather than leave the file out.

Each method lists the places in its arguments (`params`) and in its answer (`result`):

| place | meaning |
|---|---|
| `$[1]` | the second argument, whole |
| `$[0].password` | the `password` of the first argument |
| `$` | the answer, whole |
| `$[].provider.token` | the `token` of the `provider` of each row of the answer |
| `$.attributes.*` | every value in `attributes` |

A method that is not listed has no secret the source marks.

A second list in the same file, `unmarked`, holds the secrets the source does not mark. Nothing in the source finds those: they are named in the script, by method and field, and the script looks each up in the description so that the same field on a method added later is found too. How each was found is below.

## What the description does not say

Each of these was read in the TrueNAS source (`truenas/middleware` at the release's tag) and is held by a test, named after it.

**A long-running call answers a job's number unless the connection asks it to wait.** The description says what a method such as `pool.scrub.scrub` answers when it is done. A new connection is answered the number of a job at once instead, until it calls `core.set_options` with `legacy_jobs` off. 109 methods are jobs. The connection asks before it logs in. `TestALongCallAnswersItsResultNotTheNumberOfAJob`

**A message over 64 kB ends the connection.** Every other call waiting on it fails with it. Before login the limit is 8 kB, and two methods that take a file are allowed 2 MB. A call that long is refused before it is sent. `TestACallTooLongToSendIsRefusedBeforeItLeaves`

**Ten calls run at once for a connection, ten more wait, and the twenty-first is refused.** The connection sends ten and holds the rest back. `TestNoMoreCallsAreSentAtOnceThanTheNASWillRun`

**A pool's scrub and disk layout are described as having no shape.** `pool.query` and `boot.get_state` describe `scan`, `expand` and `autotrim` as records with no fields, and each list of vdevs in `topology` as a list of values of no type. A NAS writes all of them the same way every time, and they are what anything watching a pool reads: its scrub's state, times and errors, and each vdev with its disks and their error counts. The client gives them records of their own (`PoolScan`, `PoolExpand`, `PoolAutotrim`, `PoolVdev`, `PoolVdevStats`), in `sdk/pandorest/pools.go`, written from `plugins/pool_/topology.py` and the pool model. A disk that is not ONLINE carries the whole disk record the NAS last had for it, as `unavail_disk`. `TestAPoolsScrubAndLayoutReadIntoTypes`, `TestEverythingTheExporterAsksReadsIntoTheTypedClient`

**A task's state and its last run are described as having no shape.** A snapshot task's and a replication's `state`, and the `job` of a replication, a copy task, a cloud sync and a cloud backup, are described as values or records with no fields. The state is always what the NAS's replication engine keeps (`plugins/zettarepl_/state.py`): a state word, when, and an error or a reason. The job is always the record `core.get_jobs` lists. The client gives the state a record of its own (`TaskState`) and points the job at the job record, in `sdk/pandorest/tasks.go`. A replication never run reads as PENDING with no time. `TestATasksStateAndLastRunReadIntoTypes`, `TestEverythingTheExporterAsksReadsIntoTheTypedClient`

**A ZFS GUID is written as a bare number too large for a signed 64-bit integer.** `zfs.resource.query` writes each dataset's `guid` as a number, as its description says, and a GUID is an unsigned 64-bit number: about half are larger than a signed one holds, so read into one the whole answer fails. Which half a run's pool falls in is chance, so the typed sweep passed once before it failed. The client holds it as `uint64`. `TestAZFSGUIDLargerThanASignedNumberReads`, `TestEveryReadIsReadIntoTheTypedClient`

**A dataset's snapshot count is left out of its row.** `pool.dataset.query` asked with the extra `snapshots_count` adds `snapshot_count` to each row, and the row's description has no such field, so a typed read dropped it. The client adds it, in `sdk/pandorest/pools.go`, as a number that can be none, so that a row not asked for it reads apart from a dataset with no snapshots. A scrub's and an expansion's `total_secs_left` are the same: null when the NAS cannot tell, which would otherwise read as nothing left. `TestADatasetsSnapshotCountReads`, `TestAPoolsScrubAndLayoutReadIntoTypes`, `TestEverythingTheExporterAsksReadsIntoTheTypedClient`

**A dataset list asked for rows alone and given no filter stops at the pools.** `pool.dataset.query` with `retrieve_children` off goes below each pool's own dataset only when it has a filter to apply (`plugins/pool_/dataset_query_utils.py`), so asked for every dataset that way it answers the pools alone. With `retrieve_children` on it does list every dataset, but nests a copy of everything under each one inside its row. The tools ask with it off and a filter every dataset passes. `TestTheDatasetsAreListedAPageAtATimeAndDescribed`, `TestAuditSpaceFindsADatasetFillingItsQuota`

**A dataset count ignores the filters.** `pool.dataset.query` asked to `count` counts every dataset it walks before the filters are applied, so a count of the datasets on one pool, or under one dataset, is a count of them all. `dataset_list` counts the names a filtered list answers instead. `TestDatasetListIsPagedByTheNASAndSaysWhatEachHolds`, `TestTheDatasetsAreListedAPageAtATimeAndDescribed`

**An API key sent without TLS is revoked on the spot.** The login answers `EXPIRED` and the key is gone for good. An address without TLS is refused before anything is sent. `TestSettingsThatCannotWorkAreRefusedWhenTheConnectionIsMade`, `TestARevokedKeySaysANewOneIsNeeded`

**Logging in with a key and no user name is going away.** `auth.login_with_api_key` is removed in TrueNAS 27; `auth.login_ex` wants the name of the user the key was made for. Both are supported. `TestAKeyAloneLogsInTheOlderWay`

**A TrueNAS 26 takes a login in which the key is never sent, and says so only when asked.** `auth.mechanism_choices` lists the logins a NAS takes, and `SCRAM` is among them from 26.0. Each side proves it holds the key, in two calls of `auth.login_ex`, and the number of the key rides beside the user's name (`user:7`). The connection asks, and uses it wherever it is offered. `TestANewerNASIsLoggedIntoWithoutTheKeyEverBeingSent`, `TestTheNewerLoginsMessagesAreTheOnesWorkedOutByHand`

**A 25.10 cannot say which logins it takes until someone is logged in.** Asked before, `auth.mechanism_choices` fails on the session it has not got yet (`'NoneType' object has no attribute 'may_create_auth_token'`). That failure, and a NAS with no such method, are both read as a NAS that takes a key only as it is. `TestACallSendsItsArgumentsInOrderAndReadsTheAnswer` and every other test against a stand-in 25.10

**The newer login is tied to the certificate the NAS showed, and the NAS checks the tie against its own.** Something in the middle that shows another certificate and passes every message along is refused by the NAS, as is a caller that comes through a reverse proxy. The NAS lets a login in before it has proved itself, so the connection checks the NAS's proof before making any call. `TestALoginPassedAlongBySomethingInTheMiddleIsRefused`, `TestSomethingAnsweringInTheNASsPlaceIsFoundOutBeforeAnyCallIsMade`, `TestALoginIsTiedToACertificateByTheHashItWasSignedWith`

**What a NAS answers the first message with is not trusted until it has proved itself.** It names how many times the key is to be stretched, and a number in the billions would keep a caller busy for hours: the count is held to the 50,000 to 5,000,000 a NAS uses. `TestAChallengeThatIsNotOneIsTurnedAway`

**Which logins a NAS takes is said before anything is proved, so it is only believed over a checked certificate.** Something in the middle could leave the newer login off the list to be sent the key. A key is sent as it is only where the certificate was checked, or the caller says it may be. `TestAKeyIsNotSentAsItIsToANASNothingVouchesFor`

**A job is answered by its number, and so are other things.** A new user's number is a number too, so an answer that is a number does not make a call a job. The NAS says a job was added before it answers the call that added it, naming the message that asked, and that is what a started job is known by. `TestAMethodThatIsNotAJobIsCarriedOutAndSaidNotToBeOne`

**A call that waits for a job holds one of the connection's ten places until the job ends.** A dozen replications waited for would leave no room for anything else. Jobs that are started go over a second connection, left answering the number, where they hold nothing. `TestAJobThatWasStartedTakesNoneOfThePlacesCallsAreMadeIn`

**What the NAS says of a job carries the job's answer with its secrets in.** Asked how a job stands, a NAS hands anyone but itself a copy with the secrets removed, unless asked for the answer as it was (`raw_result`); what it says unasked is never the copy. Both are asked for and hidden in a trace by the job's own method, at every one of the 1,040 places. `TestAJobIsFoundAgainByItsNumberFromAnotherConnection`, `TestAJobsSecretsAreHiddenInATraceAsItsCallsWouldBe`, `TestEverySecretTheSourceMarksIsHiddenInATrace`

**A job that fails gives the number of what went wrong and not its name.** The name is what tells "not found" from "not allowed", so it is looked up: Linux's numbers, and ten of TrueNAS's own from 201 to 210. `TestAJobThatFailsIsTheErrorACallThatFailedTheSameWayWouldBe`, `TestAnErrorsNumberIsNamedAsTheNASNamesIt`

**A NAS that restarts forgets its jobs, and keeps only so many that are over.** A job being waited for is then said to be lost, not to have failed. `TestAJobTheNASForgotWhenItRestartedIsSaidToBeLost`

**Five things a NAS says of, it says once for each time it was asked.** Live figures, a followed log and three more are sent again for every subscription a connection holds, where anything else is sent once. The NAS is asked once per name however many are listening. `TestWatchingTheSameThingTwiceAsksTheNASOnce`

**A subscription ends with the connection, and the NAS can end one itself.** Nothing is kept across a restart, so everything watched is asked for again; and a log that comes to its end, or a right taken away, is said in a message of its own. `TestWatchingGoesOnThroughANASThatRestartsAndSaysThereWasAGap`, `TestTheNASEndingWhatWasWatchedEndsTheSubscriptionWithItsReason`

**Four calls carry another method's arguments or answer, or an address good for one download by whoever holds it.** `core.bulk`, `core.job_wait`, `core.download` and `core.job_download_logs` show nothing of either in a trace. `TestACallThatCarriesAnotherCallsArgumentsOrAnswerShowsNeither`

**A file goes to and from a NAS by a web request, not over the connection.** Eight methods hand a file back and eight take one (`downloadable` and `uploadable` in the description). A download is asked for with `core.download`, which answers a job and an address good for one fetch; an upload is one request to `/_upload` carrying the method, its arguments and the files, answered with the job that deals with them. An upload is let in by the key itself or by a token asked for with `auth.generate_token`, and the token is what is used, so that the key never rides on a web request. `TestAFileTheNASMakesIsFetchedWholeAndNothingOfItReachesALog`, `TestAFileIsHandedToTheNASAndTheJobThatDealsWithItAnswered`

**A NAS starts sending a file before it knows it can finish it.** One that fails part way is simply cut short, with a web answer that says all is well. The job that made the file is asked how it ended once the file stops, and its failure is the download's. `TestAFileTheNASCouldNotFinishIsSaidNotToBeWhole`

**A thing that is not there is refused as a bad argument.** Asked for a dataset, a pool or a job by an id it has nothing for, a NAS does not answer that the call failed. It answers "Invalid params", with no argument named and the number for "not there" beside the sentence. That is told apart from a real bad argument, so `IsNotFound` is true of it and `IsInvalid` is not. Found by the first live run, where the stand-in had it wrong. `TestARefusalSaysWhatKindItIs`, and live in `TestARealNASsRefusalsAreToldApart`

**Over its own socket a NAS logs a connection in as it opens.** It can see which user is at the other end, and takes root or any user it has an account for with nothing sent. The connection asks who is logged in, so that a user the NAS does not know is told so when it connects and not at its first call. `TestAProgramOnTheNASItselfIsLoggedInByWhoItRunsAs`, `TestAUserTheNASDoesNotKnowIsToldSoAndTheSocketsLoginIsOnlyForTheSocket`

**A trace hides every secret the source marks, and three it does not.** A trace hides by name and by method, not by the list above, so the list is what holds it to account: a marker is planted at each of the 1,040 places and looked for in what a trace would print. That found a mail account's password (sent as `pass`), a Kerberos keytab (`file`) and a container registry's user name being shown, and they no longer are. The source leaves three generated secrets unmarked, the answers of `auth.generate_token`, `nvmet.host.generate_key` and `tn_connect.generate_claim_token`; those are found from the description, as bare text it calls a key, a password or a token. `TestEverySecretTheSourceMarksIsHiddenInATrace`, `TestNoMethodShowsASecretItTakesByPositionOrAnswersBare`, `TestWhatATraceShowsOfAMessage`, `TestNoSecretReachesTheLogOrAnError`

**A NAS hands out two secrets it does not treat as secret.** A secret the source marks is answered as `********` to anyone who is not a full administrator. Two are not marked, so they go to anyone who may read, a read-only key included: the private keys the NAS's SSH server proves itself with (`privatekey` and the five `host_*_key` of `ssh.config`), and the key a replication encrypts what it copies with (`encryption_key` of `replication.query`). Whoever holds the first can pass for the NAS over SSH, and whoever holds the second can read the encrypted copy. Seen on a real 25.10.7 with its SSH server started: a read-only key was handed the ECDSA, Ed25519 and RSA private keys whole (676, 548 and 3,472 characters), and a replication's passphrase exactly as it was given; the NAS had no DSA or older key. They were found by reading the description for names that sound like a secret and then the source for what each holds, and a trace showed all of them until this was found. They are now in the `unmarked` list with the key `keychaincredential.generate_ssh_key_pair` answers, a marker is planted at each as for the rest, and a program that logs what it reads from either call should hide them itself. `TestEverySecretTheSourceMarksIsHiddenInATrace`, `TestWhatANASDoesNotKeepSecretIsHandedToAKeyThatMayOnlyReadAndNeverTraced`

**A query told to answer its one row, when none matches, says only `MatchNotFound()`.** With `get` true in its options a query answers a row in place of a list. When no row matches, a real 25.10.7 answered code -32001 with `EINVAL` and the reason `MatchNotFound()`, with no `ENOENT` in it; `IsNotFound` reads that as nothing there. With `count` true a query answers a number. Filters sent as `null`, where a list is described, are refused: `filters: Input should be a valid list`. `TestAQueryAnswersOneRowOrHowManyAndSaysWhenThereIsNoRow`, `TestARefusalSaysWhatKindItIs`

**An SFTP account that logs in with a key and has no password cannot be used.** TrueNAS's own code reads the password whatever else is given (`cloud_sync.py`, `RcloneConfig`), so checking or using such an account fails with `'NoneType' object has no attribute 'encode'`. An empty password beside the key is taken. `TestACloudSyncCopiesAndSaysSoWhenTheStorageIsGone`

**A service the NAS has never heard of is refused, whatever `silent` says.** `service.control` is described as answering `false` in place of an error when told to be silent, which it is by default. Told to start a service that does not exist, it was refused all the same: `service.control: nothing-by-this-name (EINVAL)`. A service that exists and will not start is what answers `false`. `TestAServiceIsStartedStoppedAndSetToStartWithTheNAS`

**When a certificate is good until is written in the NAS's own time zone, which it does not say.** `certificate.query` gives `from` and `until` as text such as `Mon Oct 12 20:04:36 2026`. The test NAS keeps the time zone America/Los_Angeles, and a certificate good until 03:04 UTC was said to be good until 20:04 the evening before. The zone is `timezone` in `system.general.config`. The NAS's own daily check of certificates compares that text with the time in UTC (`alert/source/certificates.py`), so by the source its count of days left is off by the zone's offset, seven hours here, which can move a warning by a day. `TestACertificateSaysWhenItRunsOutAndOneThatHasIsNotTakenForTheNASItself`

**A NAS will not make a bucket on S3 storage.** `cloudsync.create_bucket` with an S3 account was refused: `[EFAULT] This provider can't create buckets`. The bucket has to be there already; listing buckets works. `TestACloudSyncToABucketMirrorsEncryptsAndSaysSoWhenTheStorageTurnsItAway`

**A virtual machine runs on the test NAS.** The runner lets a machine inside a machine run, so `vm.supports_virtualization` is true and a machine with a disk started, read `RUNNING`, used its 256 MiB, and was switched off. `TestAMachineIsGivenADiskChangedCopiedAndStartedWhereItCanBe`

**A virtual machine's name is letters and digits only.** Copying one under the name `tried-copy` was refused as `vm_create.name: Only alphanumeric characters are allowed.`, though the call was `vm.clone`. `TestAMachineIsGivenADiskChangedCopiedAndStartedWhereItCanBe`

**A field can be sent under another name than the source gives it.** A mail account's password is `pass_` in the source and `pass` to a caller. The list of secrets uses the name a caller sees. `TestEverySecretTheSourceMarksIsHiddenInATrace`

**A failure can quote back what it was sent, and carries a record of where it happened.** The record holds whatever the NAS had in hand at the time. Neither is kept: the key is blanked in every error, and the record is dropped. `TestNoSecretReachesTheLogOrAnError`

**The certificate a TrueNAS comes with is made out to `localhost`.** Trusting it as an authority does not help, because the NAS is never reached by that name. Handed over as the NAS's own certificate, it is accepted by its key, whatever name and dates are on it. `TestTheCertificateANASComesWithIsAcceptedByItselfWhateverNameIsOnIt`, `TestANASIsKnownByItsKeyThroughARenewalAndAnExpiryAndNotByAnotherKey`

**A session can be ended by the NAS while the connection stays open.** The next call is answered "Not authenticated". The connection is dropped and the call after it logs in again. `TestASessionTheNASEndedIsLoggedIntoAgain`

**A user who is not an administrator is answered `********` where a secret is, whatever the secret is.** The description says `mail.config` answers its `oauth` as an object, `system.general.config` its `ui_certificate` as an object and a user's `password_history` as a list. A full administrator gets those. Anyone else, unless they hold the role that may change that part of the NAS, gets the one piece of text in place of each, so an answer read strictly as the description has it fails to read for a user who may only read, which is exactly the user a program that watches a NAS should be given. Seen on a real NAS and then read in the source (`dump_result` in `main.py`, `SECRET_VALUE` in `api/base/types/string.py`). `Secret` in `sdk/truenasrpc` reads either. Every place a real NAS kept something back is a place the secrets list names, and the administrator is shown them all. `TestASecretTheNASKeptBackIsReadAsOneAndNeverPrinted`, `TestEveryReadIsAnsweredTheWayItsDescriptionSays`

**The audit log cannot be listed without a limit.** The description says `audit.query` needs no argument. Called with none it is refused: its options have to hold a limit on the rows, or ask only for a count. `TestEveryReadIsAnsweredTheWayItsDescriptionSays`, `TestReadsThatAreToldWhatToReadAnswerTheWayTheirDescriptionSays`

**A disk has no id.** Every other kind of thing a NAS lists has an `id`, and is fetched by it. `disk.get_instance` is described as taking an `id` too, but a disk's row has none: it is fetched by its `identifier`. `TestWhatIsListedIsFetchedByItsIDAndWhatIsNotThereIsMissing`

**A NAS takes twenty logins a minute from one address.** The twenty-first is kept waiting between one and ten seconds and then refused with `[EBUSY] Rate Limit Exceeded`, and so is every one after it until a minute has passed since the count began. It counts calls made before logging in, by method and by the address they come from (`authorize_method_call` in `main.py`, `utils/rate_limit/cache.py`). `IsTooManyCalls` is true of the refusal. A connection that is refused leaves the NAS alone for longer each time and gets in by itself once the minute is up; a program that makes a connection for everything it does will not. Found when the live tests each made a connection of their own. `TestMoreLoginsThanANASTakesInAMinuteAreRefusedAndAConnectionWaitsItOut`

**A disk is named two ways.** Making a pool and attaching a disk to one take the disk's name (`vdd`). `pool.replace` is described as taking the "name of the new disk" as well, and takes its identifier (`{serial}TNTEST3`): the source looks the disk up by that. `TestADiskThatDiesIsNoticedAndASpareTakesItsPlace`, `TestASecondPoolIsMadeOnOneDiskGivenASecondAndRemoved`

**A snapshot that something rests on is refused removal, two different ways.** One that a copy was made from is refused as a bad argument: `options.defer: Please set this attribute as 'tank/kept@before' snapshot has dependent clones: tank/kept-copy`. One that is held fails as a call: `[EFAULT] cannot destroy 'tank/kept@before': dataset is busy`. `TestASnapshotBringsBackWhatWasThereIsCopiedHeldAndRemoved`

**A dataset is not renamed until the caller says the risk is understood.** `pool.dataset.rename` is refused as a bad argument unless `force` is true: `No safety checks are performed when renaming ZFS resources; this may break existing usages. If you understand the risks, please set force and proceed.` The description gives `force` a default of false and says nothing of it being needed. Its `recursive` is not for taking along what is under a dataset, which goes with it anyway: set on a dataset it fails with `recursive rename must be a snapshot`. `TestADatasetIsMadeChangedRenamedAndRemoved`

**A dataset's note is among its user properties.** The description lists `comments` as a name of the dataset's own. A real NAS answers the note under `user_properties.comments`, with a `value` like any other setting, and has no `comments` beside it. `TestADatasetIsMadeChangedRenamedAndRemoved`

**A share's options lack a name the description says is always there.** An SMB share made with nothing said of its options is listed with `options` that have no `purpose` in them, though the description requires one. `TestEverythingTheExporterAsksIsAnsweredToAKeyThatMayOnlyRead`

**A pair of disks has no `disk`.** In a pool's topology only a disk says which disk it is. The pair above it has no such name at all, not a name with nothing in it. `TestEverythingTheExporterAsksIsAnsweredToAKeyThatMayOnlyRead`

**A dataset's key comes two ways.** Asked for as an answer, `pool.dataset.export_key` gives the key alone, 64 characters. Fetched as a file, it is a JSON object of the dataset's name and its key. `TestAnEncryptedDatasetIsLockedUnlockedAndGivenANewPassphrase`

**A pool takes one scrub task.** It is given one when it is made, and a second is refused: `A scrub with this pool already exists`. `TestAPoolIsScrubbedOnAScheduleAndItsCareIsSetAndReadBack`

**A machine can be described on a NAS that cannot run one.** `vm.create` makes a virtual machine on a NAS with no virtualization, as the test NAS is. `TestEverythingTheExporterAsksIsAnsweredToAKeyThatMayOnlyRead`

**Not every change can be made a piece at a time.** Most of a NAS's updates change what is sent and leave the rest, and the description marks nothing in them as needed. Some want more than the description says. An alert service is changed whole: `alertservice.update` with only a new level is refused for want of its `name` and `attributes`. The mail page wants `fromemail` with any change, and the UPS page its `driver` and `port`. `update.update` refuses any change that does not name a profile the NAS offers (`Invalid profile`). And the rules for passwords (`system.security.update`) are refused on a NAS without a licence: `This feature can only be enabled on licensed iX enterprise systems.` `TestOneOfEachKindOfThingANASKeepsIsMadeChangedAndRemoved`, `TestOneSettingOnEachPageIsChangedReadBackAndPutBack`, `TestThePagesThatWillNotTakeAChangeSayWhy`

**Which methods only read is not said.** The description lists the roles that may call each method, and a method the read-only administrator role may call is nearly always a read: 386 of the 769. Five are not, and nothing in the description tells them apart: a read-only administrator may make, change and remove API keys of its own (`api_key.create`, `api_key.update`, `api_key.delete`) and send a ticket to TrueNAS's support (`support.new_ticket`, `support.attach_ticket`), which the source gives it by name. So the role says who may call a method, not that it changes nothing, and a program that promises only to read cannot go by the role alone. Twenty-five methods are given to that role by name; each was read in the source, and a release that adds one fails a test until it has been too. 33 methods list no role at all: logging in, subscribing, asking after jobs, and a user setting their own password. `TestEveryMethodTheReadOnlyRoleIsGivenByNameHasBeenLookedAt`, `TestEveryMethodIsSortedByHowItCanBeTested`

## What a real NAS answers, held to the description

Everything generated from the description is only as right as the description. So the live tests call every read that needs no argument (252 of them) on a real TrueNAS, as a user who may only read, and hold each answer to what the description says it is: a name it says is always there, a name it does not have, a value of another kind, a value outside the ones allowed. Whatever a NAS lists and can hand over one at a time is fetched by its id as well, and an id nothing has is asked for, since "it is not there" has to be the same answer whatever was asked for. `TestEveryReadIsAnsweredTheWayItsDescriptionSays`, `TestWhatIsListedIsFetchedByItsIDAndWhatIsNotThereIsMissing`

The first time this ran, on 13 October 2026, 246 of the 252 answered as described, and "it is not there" was the same answer for every one of the 56 kinds of thing fetched by an id. Three reads are refused on a NAS like the test one, each for a reason that is its own: `app.available_space` until a pool is chosen for apps, `tn_connect.get_registration_uri` until the NAS is joined to TrueNAS Connect, and `audit.query` as above. The other three were secrets kept back, above. Asked by the administrator, who is shown the secrets, all 249 that answer do so as described.

The secrets list, which is made from the source, held against a real NAS: everything it kept back from the user who may only read (14 places in 9 methods, from an API key's hash to the SNMP passwords) is a place the list names.

Thirty-four reads that have to be told what to read are asked about what the journey made, and answer as described. One of them answers by the state the NAS is in: `sharing.smb.share_precheck` refuses on a NAS with no user who may use SMB (`TrueNAS server must be joined to a directory service or have at least one local SMB user before creating an SMB share.`), and answers once there is one. `TestReadsThatAreToldWhatToReadAnswerTheWayTheirDescriptionSays`

What a real NAS does some other way is written down beside those tests (`surprises`, in `acceptance/truenasrpc/reads_test.go`), each with why. One that stops being true fails too, so the list stays what is known and does not become a way to quiet a test.

The run ends by saying how many of the NAS's methods the tests called, by kind, and which were not: how much of the API is tested is counted, not claimed. Every connection the tests make is traced to do it, so every answer a real NAS gives also passes through the code that hides secrets, and a key the tests made turning up in any line fails the run. `TestTheRunSaysHowMuchOfTheAPIItTriedAndShowedNoKey`

**A machine copied a moment before can fail to start.** Now and then `vm.start` on a machine just copied with `vm.clone` is refused with `[EFAULT] Domain not found: no domain with matching uuid`, and a few seconds later it starts. It has happened once on the test NAS. The test asks again for up to half a minute when it is refused that way. `TestAMachineIsGivenADiskChangedCopiedAndStartedWhereItCanBe`

## How a NAS says something is wrong

None of this is in the description: an alert's text is whatever the NAS writes, and the state a task keeps has no shape there at all. Each was read from a real NAS that was given the problem, and the tests that give it the problem hold what was read.

**A pool with a disk gone says so itself, at once, and in an alert within a minute or two.** With one disk of a pair taken out, the pool's `status` is `DEGRADED`, `healthy` is false, and the disk's own `status` in the topology is `OFFLINE`. The alert is class `VolumeStatus`, level `CRITICAL`, and both clear when the disk is back. The alert's text is HTML, with a list in it, and names the disk by a model it does not have: `Pool tank state is DEGRADED: One or more devices has been taken offline by the administrator. Sufficient replicas exist for the pool to continue functioning in a degraded state.<br>The following devices are not healthy:<ul><li>Disk None TNTEST1 is OFFLINE</li></ul>`. `TestAPoolThatLosesADiskSaysSoAndIsWholeAgainWhenTheDiskIsBack`

**A pool with a dead disk can still call itself `ONLINE`.** A disk taken away from under the NAS, so that every read and write of it fails, is `FAULTED` in the pool's topology within seconds of the next write, and the pool's `healthy` is false. Its `status` still read `ONLINE`, and the alert said so too: `Pool tank state is ONLINE: One or more devices are faulted in response to persistent errors. Sufficient replicas exist for the pool to continue functioning in a degraded state.` So a pool's `status` is not to be gone by: `healthy`, and the `status` of each disk under it, are what say a pool is in trouble. What was written with the disk dead is all there, and with a spare put in its place the pool is whole again and the alert clears. `TestADiskThatDiesIsNoticedAndASpareTakesItsPlace`

**A pool that was just removed can still be in the alerts.** For a minute or so after a pool was removed, the NAS listed a critical alert for it: `Pool scratch state is OFFLINE: None`. An alert is what the NAS thought when it last looked, so one that names a pool has to be held against the pools there are now.

**The list of disks says nothing of a dead disk.** `disk.details` lists it as the pool's, with its size, like the disk beside it. Only the pool's topology knows.

**A pool on one disk is healthy as far as the NAS is concerned.** It reads `ONLINE` and `healthy`, with the one disk where a pair has its mirror: the top of its topology is of type `DISK`, not `MIRROR`. That nothing stands behind that disk is something only the layout says. `TestASecondPoolIsMadeOnOneDiskGivenASecondAndRemoved`

**How full a dataset is has to be read from the dataset.** The NAS looks at quotas itself once an hour and at how full a pool is every five minutes, so its alerts say nothing for a while. A dataset's `used`, `available` and `refquota` (each with the number under `parsed`) are right as soon as the file is written. A file that would go over the limit fails with `[Errno 122] Disk quota exceeded`. `TestADatasetFilledToItsLimitShowsHowFullItIsAndTakesNoMore`

**Space kept aside counts as used where it matters.** A volume made with its space reserved takes that space from everything else in the pool though nothing was written to it. What the pool's top dataset says is `used` and `available` shows it. The pool's own `allocated` is a count of what has been written and still reads as next to nothing, so a check of space that reads only the pool calls a pool with nothing left empty. `TestAPoolWithMostOfItsSpaceSpokenForShowsLittleLeft`

**A dataset that is read-only or locked says so when written to or read.** A file for a read-only dataset fails with `[Errno 30] Read-only file system`. A locked dataset reads as `locked` with `key_loaded` false, and what it held is not there to be read until it is unlocked; asked first (`pool.dataset.encryption_summary`), the NAS says whether a passphrase would open it. `TestADatasetIsMadeChangedRenamedAndRemoved`, `TestAnEncryptedDatasetIsLockedUnlockedAndGivenANewPassphrase`

**A replication that works says `FINISHED`, and the copy holds what the dataset held.** Run again after the dataset changed, the copy holds the change and one more snapshot. `TestAReplicationCopiesADatasetAndThenOnlyWhatChanged`

**How hot a disk is comes with what is too hot for it, on request.** `disk.temperatures` answers a number for each disk that can say, and nothing for one that cannot, which most disks in a virtual machine cannot: nothing means not known, not cold. Asked with its second argument true, it answers the two numbers together for each disk, how hot it is and what the disk itself says is too hot, which is the pair the NAS's own alert compares. The test machine's NVMe disk reads 49.85 degrees. The description gives the answer no shape at all. `TestADiskSaysHowHotItIsAndWhatIsTooHotForIt`

**A copy task that fails says so three ways, and its log says why.** The run fails (`[EFAULT] rsync command returned 10 - SOCKETIO. Check logs for further information.`), and the job's log, fetched like a file, holds what rsync said: `rsync: [sender] failed to connect to 127.0.0.1 (127.0.0.1): Connection refused (111)`. Beside that, the task's row keeps the job of its last run with `state` `FAILED`, and an alert of class `RsyncFailed`, level `CRITICAL`, is raised at once: `Rsync "PUSH" task for "/mnt/tank/alpha" failed.` That alert stays until somebody dismisses it, and dismissed it is still listed, marked `dismissed`; brought back (`alert.restore`) it is as it was. `TestATaskThatCannotReachWhereItCopiesToIsSaidToHaveFailed`

**A task keeps how its last run went under `state`, which the description gives no shape.** Read from a real NAS, for a snapshot task and a replication alike: `{"state": "PENDING"}` before it has ever run; `{"state": "FINISHED", "datetime": {"$date": ...}, "last_snapshot": "tank/alpha@kept-2026-10-12_22-08"}` after a run that worked; and `{"state": "ERROR", "datetime": ..., "error": "...", "last_snapshot": ...}` after one that did not, with the reason in words. A failed task that is enabled is in the alerts within a minute or two as well, class `SnapshotFailed` or `ReplicationFailed`, level `CRITICAL`. `TestASnapshotTaskKeepsHowItsLastRunWentAndSaysSoWhenItFails`, `TestAReplicationThatWouldOverwriteWhatIsThereFailsAndIsSaidToHave`

**A snapshot task run twice in one minute fails the second time.** Its snapshots are named by the minute, so the second finds the name taken: `cannot create snapshot 'tank/alpha@kept-2026-10-12_22-08': dataset already exists.` It is the easiest honest way to have a snapshot task that failed.

**A disk that gives back what was never written leaves the pool `ONLINE`, and so does data that is lost.** One disk of a pair was written over from under the NAS and the pool scrubbed. The pool read `status` `ONLINE`, `healthy` false, `status_code` `FAILING_DEV`, with 1,925 counted against that disk under `stats.checksum_errors` and none against the other, and the scrub (`scan.errors`) left nothing unrepaired. Both disks were then written over and the pool scrubbed again: `status_code` `CORRUPT_DATA`, 1,905 errors the scrub could not repair, and still `ONLINE`, with both disks `ONLINE` too. The alert, class `VolumeStatus` and `CRITICAL`, said `Pool damaged state is ONLINE: One or more devices has experienced an unrecoverable error. An attempt was made to correct the error. Applications are unaffected.` after the first scrub, and still said exactly that read straight after the second, since the NAS looks again only once a minute. A file both copies of were written over still read back whole, from memory. A check of a pool has to read `status_code`, `scan.errors` and each disk's counts; the pool's state, each disk's state and the alert's text all said less than had happened. `TestAScrubFindsADiskThatLiesRepairsItAndSaysWhatCouldNotBeRepaired`

**A replication whose other end is gone fails at once and says why three ways.** The run fails with `[EFAULT] Unable to connect to port 22 on 127.0.0.1.`, the task's `state` is `ERROR` with the same words, and an alert of class `ReplicationFailed`, level `CRITICAL`, says `Replication "a copy sent over SSH" failed: Unable to connect to port 22 on 127.0.0.1..` The next run that works clears the alert. Setting up the connection to another NAS starts that NAS's SSH server and sets it to start with the NAS, unasked. `TestAReplicationOverSSHCopiesAndSaysSoWhenTheOtherEndIsGone`

**A cloud sync whose storage is gone says so three ways, its alert a level lower than the rest.** The run fails with what rclone said, e.g. `Failed to create file system for "remote:/mnt/tank/storage/kept": NewFs: couldn't connect SSH: dial tcp 127.0.0.1:22: connect: connection refused`; the task's row keeps its last job as `FAILED`; and an alert of class `CloudSyncTaskFailed` says `Cloud sync task "a copy kept somewhere else, renamed" failed.` at level `ERROR`, where a failed copy task, replication or pool is `CRITICAL`. `cloudsync.credentials.verify` then answers `valid` false with the same words. The next run that works clears the alert. `TestACloudSyncCopiesAndSaysSoWhenTheStorageIsGone`

**A cloud sync to storage that says it is unavailable keeps trying.** Against S3 storage answering every request `503 ServiceUnavailable`, a run was still going after fifteen minutes, rclone asking again and again; storage that turns the NAS away (`403 AccessDenied`, as when its key is taken back) fails the run within a second. Anything that waits on a cloud sync needs a limit of its own. `TestACloudSyncToABucketMirrorsEncryptsAndSaysSoWhenTheStorageTurnsItAway`

**A cloud backup works and fails like a cloud sync.** Each run keeps a snapshot, listed with its id, host and paths, and one is brought back whole; told to keep two, a third run forgets the oldest. Nothing that reaches the storage can be read there. A run the storage refuses fails with what restic and rclone said, the task's last job reads `FAILED`, and an alert of class `CloudBackupTaskFailed` says `Cloud backup task "the nightly backup, renamed" failed.` at level `ERROR`. `TestACloudBackupIsMadeListedBroughtBackAndSaysSoWhenTheStorageTurnsItAway`

**What rests on a locked dataset says so in its own row, and a task on one ends as if it worked.** With the dataset locked, an SMB share, an NFS share and a copy task on it each read `locked` true. Running the copy task copied nothing, its last run read `SUCCESS`, and only an alert said otherwise: class `TaskLocked`, level `WARNING`, `Rsync task "/mnt/tank/behind-a-lock" will not be executed because it uses a locked dataset.` Nothing was said aloud of the shares. A check has to read `locked` on each share and task, and not trust a task's last run while its dataset is locked. `TestWhatRestsOnALockedDatasetSaysItIsLocked`

**An app that fails as it starts reads `CRASHED`.** A custom app whose one container exits with an error is listed with `state` `CRASHED`, and its container under `active_workloads.container_details` with `state` `crashed`; the app beside it, still running, is unaffected. An app that is stopped reads `STOPPED`. `TestAnAppIsRunStoppedAndRemovedAndOneThatFailsSaysSo`

**A restart takes about a minute and a half, and a connection rides it out.** Told to restart, the test NAS stopped answering within 13 seconds and was back and ready 1 minute 27 seconds after it was told. The run's open connections logged in again by themselves, and a subscription was told it had missed something. After it, a dataset kept under a passphrase was locked until given it again, a service set to start was running, and the tasks kept how their last runs went: a copy task that had failed still read `FAILED` with when it finished, its job now with no number, since the NAS keeps the record of a task's last run and not the job. `TestARestartIsRiddenOutAndWhatIsDifferentAfterItIsRead`

**A replication will not overwrite files.** Copying a dataset onto one that holds files and shares no snapshot with it fails, and says which file it found: `Target dataset 'tank/beta' does not have matching snapshots but has data (e.g. 'in-the-way.txt') and replication from scratch is not allowed. Refusing to overwrite existing data.`

## Making a NAS to test against

TrueNAS documents only an install by someone at a keyboard. Its installer also answers a small API of its own while it sits at its menu (`truenas/truenas-installer`, read at the release's tag): a websocket on port 8080 that lists the disks, installs onto the ones named with an administrator's password, says how far along it is, and switches the machine off. That is what `.scripts/testenv.sh` drives to make the NAS the live tests run against. `TestTheInstallerIsDrivenWithNobodyAtTheKeyboard`, `TestAnInstallThatCannotBeSureOfItsDiskOrIsRefusedSaysSo`

Another repository runs its own live tests against this NAS: truenas-exporter calls `.scripts/testenv.sh` (`image`, `up`, `down`, `logs`), reads the lines `up` prints, and keeps the installed disk by the same two files this repository does. A change to any of those is a change for it too.

Asked to (`TRUENAS_TEST_FURNISHED=1`), setting the NAS up also furnishes it: a user who may use SMB, a share of each kind, an iSCSI target, a virtual machine that is described and not running, a snapshot task that has run, a replication that has not, and a copy task whose one run failed. `acceptance/layout` names each. `TestANASIsFurnishedWithOneOfEachThingAndFurnishingItAgainChangesNothing`

The machine has six disks: the one TrueNAS is installed on, four plain ones for pools, and one NVMe disk. The NVMe disk is there because it says how hot it is, and the plain ones say nothing, so without it there would be no temperature to read.

The installer lists no disk under 8 GB, and names disks as the machine happens to find them, so the disk to install onto is told from the others by its size.

Seen on the first run, on a GitHub runner, 13 October 2026: the installer disc starts that API unasked and answers half a minute after the machine starts; the install itself takes a little over a minute; the installed NAS takes a minute and a half to come up the first time; and a virtual disk's serial reaches the NAS as it was given. Fetching the installer disc, at seven minutes, is most of the wait.

## Not yet held by a test

- a query can answer a list of rows, one row or a count, and the description of the one row leaves out the shape of any model inside it: `cloudsync.query` describes a row's `credentials` in full in the list, and as a title with no shape in the single row
- a time of day, a day, and an address with its network, as TrueNAS writes them its own way: none has been seen in a real answer. The description has 5 places that could hold the last (in `smb.config`, `smb.update` and `docker.update`). The other two forms have been seen, and the live run lists every place it meets one: a moment (`{"$date": ...}`) in `system.info`, a pool's scan times, a dataset's and a snapshot's creation, a boot environment, an API key, a session and a user's last password change; and a set (`{"$set": [...]}`) in `system.security.config`, as its `password_complexity_ruleset`, which the description calls a list
- of the sixteen methods that take or hand back a file, a real NAS has been sent and asked for files through `filesystem.put`, `filesystem.get`, `pool.dataset.export_key`, `pool.dataset.export_keys` and a job's log; the rest have only been run against the stand-in, written from the 25.10.7 source (`apps/file_app.py`). Whether a NAS serves files through its own socket was not checked, so both ways are refused there
- the newer login has only been run against the stand-in, never a real TrueNAS 26. The stand-in's half was written from the 26.0.0-BETA.3 source and TrueNAS's own Go client logs into it every way this connection does, but what a real NAS answers a revoked key with in the newer login is a guess (the stand-in refuses it as a wrong key)
- seen in a real 25.10.7's answers by truenas-exporter, and waiting for the generated client to be held by a test here:
  - a pool's `fragmentation` is text (`"14"`) where a vdev's is a number
  - a scrub's percentage can pass 100
  - a certificate's `from` and `until` are text such as `Wed Dec 23 12:57:57 2026`, where other times are `{"$date": milliseconds}`
  - `disk.temperatures` answers `null` for a disk that does not report one
  - `pool.dataset.query` with `flat` and `retrieve_children` both on still nests each dataset's children inside its row
